## 2. Index-only depth-7 table (15-move searches)

`experimentDiskDepth6 --table-depth 7` (commit 5897dbf). The depth-7 set
(6-4: 46.5 billion states, ~750 GB as states) is never stored: each pass over
the depth-6 table keeps the 64-bit keys of the children in a RAM-sized group of
partitions, sorts and de-dupes them, and writes the same compact index as the
depth-6 table (Bloom + 16-bit fingerprints + bucket offsets, ~3.7 B/state,
166 GB for 6-4). A fingerprint hit is confirmed exactly by checking that one of
its one-move neighbours is in the exact depth-6 table.

- `--d7-partitions N --d7-first-partition F` builds/probes only a slice of the
  256 key partitions, for cheap tests against known solutions.
- Verified: 6-2 12 moves `<2,3,7>` on partitions [137,147) found exactly the 2
  middles and 20 solutions in that slice; 10-3 13 moves `<3,3,7>` on [0,16)
  found exactly 4 middles and 148 solutions. The depth-6 path still gives 6-2's
  64 solutions.
- 6-4 at 15 moves: build 2 h 10 min (52 passes), search 10 passes of 2.59 T
  left states (58-78 min each), 3.73 M fingerprint hits, 135 past the depth-6
  index, 0 confirmed.
- Sizes measured: depth-7 is ~30x depth-6. A depth-8 table would be ~1-3 T
  states (~4-12 TB as an index), not practical here.

## 3. Scheduler `mbq` and progress reporting

`python/scheduler/mbq.py` (commits 8e844d3, 9abc825, b382c56), standard
library only:

- Persistent queue (`python/scheduler/state/`, git-ignored), one job at a time,
  never while another solver process runs; waits for disk space; runs a copy
  of the solver; re-adopts a running solver after a server restart.
- Validates, promotes and records results; `--until N` escalates one move at a
  time; deletes only tables it created; never commits.
- CLI: `daemon`, `status`, `add`, `queue`, `history`, `log`, `cancel`, `pause`,
  `resume`, `shutdown`.
- **Dashboard** at http://127.0.0.1:8766/: running job, phase steps, progress
  bar and ETAs, live log with a "now:" line during quiet steps, queue, finished
  jobs, solved count, queue estimate, free disk, pause/resume/cancel. It only
  answers requests for 127.0.0.1/localhost, and commands need an `X-MBQ`
  header, so other web pages cannot drive it.
- Solver side: `src/utils/progress_reporter.hpp` writes a small JSON status every
  5 s from a background thread (one atomic add per seed on the hot path), and
  log lines are flushed as written. **Overhead measured at +0.03%** (A/B on 6-4
  13 moves: 298.86 s vs 298.94 s), against the 0.5% limit.
- Fixed while testing: `tasklist` took 20-40 s with every core busy (status
  timed out), replaced by a Toolhelp snapshot (11 ms); slow validation moved
  out of the lock.

## 4. Speed work on the probe

| Change | Result |
|---|---|
| Index buffers allocated once and reused across passes (2f90ae9) | Correct (6-2 forced to 4 passes: identical 64 solutions); later passes load in 0.25-0.6 s; no measurable speed change single-pass (318.4 vs 318.1 s) |
| RAM budget = free RAM - max(3 GB, 10%) - seed memory, instead of 60% of free (2f90ae9) | 16.6 GB vs 12.8 GB on 32 GB; 12-1/12-5 (13-16 GB indexes) would have run in 1 pass instead of 2 |
| Probe self-calibration (bbfa310): first ~20 s of the search rotate real seeds through batch sizes 32/64/128, plain or pipelined, then use the fastest; cached per machine | Correct for every variant (6-2); 6-4 13 moves A/B: 322.1 s -> 318.4 s (**-1.1%** net). Picks 128/plain here; pipelining never helped |

Findings:
- On 6-4 13 moves, ~75% of the search time is lookups and ~25% generating
  positions. Memory bandwidth is not the limit (~17 GB/s of ~34 GB/s used, and
  27% less bandwidth after the RAM change made no difference). Pipelining not
  helping suggests page walks / raw latency rather than too few reads in flight.
- **Large pages** were unavailable all of 2026-10-06 before the reboot
  (fragmented memory), and on 6-4 they made no difference anyway (298.6 s with,
  298-300 s without). After the reboot they work again.
- The MuMu Android emulator runs constantly (the user keeps it on). Measured
  ~8% of the CPU while the solver runs. Windows Task Manager's Processes and
  Details tabs mis-attribute the solver's CPU to MuMu and do not list
  `mbq_ssd.exe`; Resource Monitor (`resmon`) shows it correctly. `lodctr /R`
  did not fix Task Manager.

## 8. Discussions and decisions (no code)

- **GPU**: the stream + lookup loop suits a GPU (est. 10-20x). Plan: CUDA on the
  RTX 5060 Ti (arriving Oct 19; the current GTX 1660 SUPER can be used to start),
  kept portable to HIP for an RX 9070 XT (~1.4-2x a 5060 Ti for this, but HIP on
  Windows for RDNA 4 is uncertain); 2x Radeon Pro Duo (Polaris) would need
  OpenCL. Rough guess for 6-4 at 15 moves: ~30-45 min on one good GPU.
- **Splitting across machines** works almost linearly (shard seeds or
  partitions; only candidate lists cross the network). Not built.
- **Go** would be ~1.5-3x slower for the hot loops (no pext/pdep or prefetch
  intrinsics, generics, bounds checks, GC); fine for orchestration.
- **Reaching 80/100**: everything up to 15 moves is feasible on this PC, 16 on
  fat boards; 17+ needs the GPU or a new algorithm (pattern-database IDA*).
