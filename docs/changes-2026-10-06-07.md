## 5. The SSD (X:, Team T253 1 TB SATA)

**Symptom:** depth-6 builds had grown from about 6 min (2.3 B states) to 43 min
plus 12 min of index (16-3, 6.7 B), while the search rate stayed flat at about
265 M/s. The build was disk-bound.

**Measured on 10-06 evening:**
- A sustained write test with fsync gave 32 MB/s once the drive's fast cache
  was exhausted.
- During a build, resmon showed the disk 100% busy at about 70 MB/s, with
  about 0.1 s per write.
- TRIM is enabled.
- Memory fragmentation was ruled out as the cause.

**Tried:** `--ram-build` (79a7eb5). It regenerates the depth-6 children per
RAM-sized group of partitions, sorts and de-dupes them in memory, and writes
sorted partitions plus the index once, with no raw spill.
- Correct: 6-2 gave the identical 64 solutions.
- Slower here: 475 s against about 200 s, because the disk build's writes had
  been landing in the OS file cache.
- Kept opt-in.

**Fix:** stop writing tables at all (sections 6 and 7).

**Re-measured on 10-07 morning, after the drive had idled since 04:00:**
- A 12 GB write test (64 MB fsync'd chunks, file deleted afterwards) averaged
  333 MB/s.
- Per GB it ran 272, 273, 282, then 358-360 MB/s.
- The drive recovers when idle. Back-to-back 70-140 GB table builds had
  exhausted it.
- This no longer matters, because the solver writes nothing but solution files.

## 6. No-table depth 6 (04fbc37, da1e3b8)

The default for `--table-depth 6` unless a complete table and index are already
on disk. `--disk-table` forces the old path.

### Steps

1. Build the exact depth-5 frontier of the goal in RAM (`buildUniqueNoneDepthFrontierB1B2<5>`,
   45-165 M states, under 3 GB).
2. Count pass: expand every depth-5 state by one move (`emitNoneChildren`) and
   count the raw children per partition (`mixKey` top 8 bits, 256 partitions).
3. De-dupe ratio: collect partition 0's keys, sort and unique them. The ratio
   was 0.49-0.64. Each partition's estimate is raw x ratio x 1.02 + 1024.
4. Size the index like the disk one:
   - Buckets: 4 states per bucket (`TARGET_STATES_PER_BUCKET`).
   - Bloom filter: 10 bits per state, sized from the largest partition.
5. `streamAndProbe` takes an optional `IndexBuilder` callback, plus RAM to keep
   back for it. Instead of reading the index from disk, each pass's slice is
   built in RAM:
   - Regenerate depth 6, keeping only the keys in this pass's partitions, in
     sub-groups whose raw keys fit the leftover RAM.
   - Stage each thread's keys in buffers of 1024 and spill them to the
     partition arrays with one atomic add per buffer.
   - Sort and unique each partition, then fill the 16-bit fingerprints, the
     bucket offsets and the Bloom filter.
6. Calibration, seeds and passes are unchanged.
7. Verify: build a 2^27-bit bitmap on key bits 20-46 of the candidates. Then
   regenerate depth 6 once more; for each bitmap hit, binary-search the
   key-sorted candidates and compare full states. The confirmed states are the
   middles, and recovery is unchanged.

### Notes

- **De-dupe is by 64-bit key, not by state.** `StateHash` is not a perfect hash
  (its locality is deliberate), so distinct states sometimes share a key. 9-3's
  "unique" count was 2,173,039,544 against the exact table's 2,173,198,627:
  159,083 fewer. This is harmless, because lookups are by key and the final
  check compares full states.
- **RAM accounting fix (da1e3b8).** The key-buffer budget subtracted the index
  buffers from free RAM even when they were on large pages, which are already
  out of free RAM. That left about 2.5 GB for keys, and 17-5 regenerated depth
  6 about 9 times (index 578 s). After the fix, untouched normal-page buffers
  still count as used, but large-page ones don't. The log now says
  `index build: X GB for keys -> about N regeneration(s)`. 18-3 needed 3
  regenerations (163 s).

## 7. No-table depth 7 (8ad8a0a)

**Why:** in a meet-in-the-middle split, the left (start) side does almost all
the work, about 265 M states/s. Its size is set by left depth = total - table
depth:

| Split | Left depth | 6-4 left states |
|---|---|---|
| `<5,3,6>` = 14 moves | 8 | 2.59 T |
| `<5,3,7>` = 15 moves (the 13.4 h 6-4 run) | 8 | 2.59 T per pass |
| `<4,3,7>` = 14 moves | 7 | about 84 G (about 30x fewer) |

So 14 moves with a depth-7 goal side moves the work into building the depth-7
index. That index is about 37-47 B unique states on a 2x2 board, too big to
store but small enough to rebuild in RAM a slice at a time.

### Design

- The depth-5 frontier is kept in RAM (46-51 M states).
- **Generator:** the canonical 2-move stream
  (`PermStream<B1B2>::streamDepth<ASCENDING, 2>`), the left side's own
  generator. It emits no same-lane pairs and one order per commuting pair.
  - About 1575 descendants per depth-5 state on 2x2 boards, against about 2285
    raw two-level children: 31% fewer.
  - It runs at about 520 M keys/s on 16 threads.
  - Every state at exact depth 7 is a depth-5 state plus two moves that don't
    reduce to fewer, so the stream covers them. States at smaller depth also
    appear; they only cost index space.
- **Count pass, once:** an exact count of raw fingerprints per bucket.
  - Counts are u16: 2^23 buckets per partition, about 32-64 raw keys per bucket,
    largest bucket seen 3229.
  - The count array is 4.29 GB, on large pages.
  - The same pass samples 1/4096 of the keys to measure the de-dupe ratio (0.52-0.58), which sizes the Bloom filters.
- **Index slices:** partition regions are sized by raw count. Each pass:
  - Bucket offsets come from a prefix sum of the counts.
  - Regenerate depth 7 and write every in-range key's 16-bit fingerprint at its
    bucket cursor, then set its Bloom bits.
  - Sort and de-dupe each bucket by fingerprint, compacted to the front of its
    region. Equal fingerprints in one bucket answer lookups identically.
  - The lookup code (`FingerprintRange::issue/finish`) is unchanged.
- **Verify:** regenerate depth 7 with the same stream, using the same bitmap,
  binary search and full-state compare as depth 6. Recovery uses the existing
  `recoverWithTableDepth<7>`.
- **6-4's depth-7 index on disk** (166 GB, kept for 16 moves) is still used by
  the old path when present.

### Getting it fast: the rounds on 6-2 at 12 moves (72-104 B keys)

| Round | Change | Measured |
|---|---|---|
| 1 | Generic two-level `emitNoneChildren` (104.3 B raw keys), atomic u16 increments | Count pass 896 s = 116 M keys/s. Locked random read-modify-writes cannot overlap cache misses |
| 2 | Route keys to the thread owning their partition (no atomics) | Still over 10 min; stopped |
| 3 | Canonical 2-move stream (72 B keys) | Per 6.5 B keys: generate 12.9 s, drain 60.7 s (107 M/s). The drain was the bottleneck |
| 4 | Owner groups its keys by (partition, top 6 bucket bits) before counting; counts on large pages | Drain 36.6 s per 6.5 B. Grouping was 9.6 s of it, counting 23.0 s |
| 5 | Large pages for the grouping buffer | No change (36.3 s). TLB was not the issue |
| 6 | Full LSD radix sort by bucket (3 passes of 10 bits) | Worse: count pass 720 s (generate 136, sort 583). Scattering to 1024 places per pass thrashes the cache |
| 7 | Back to grouping, with 4x bigger blocks (400 M keys in flight, 6.4 GB): about 6 keys share each cache line of counts per block instead of about 1.5 | **Count pass 383 s** (generate 144, group+count 237). First fill pass 414 s (group+write 278) |
| 8 | Fill: group by 8 bucket bits for the fingerprint and offset writes, plus a second grouping by the top bits of the Bloom hash for the Bloom writes | **Fill pass 318 s** (generate 107, group+write 183) |

**Final 6-2 test (`<2,3,7>`, 12 moves):** count 6.3 min, then 6 passes of
5.3-5.7 min (the last one is a small 6-partition pass at 104 s). Verify took
2.7 min, 38.3 min in total.
- `middle validation ... expected 5, missing 0, extra 0 -> EXACT MATCH`.
- `solution validation: known 64, recovered 64 -> IDENTICAL SET`.

**Notes:**
- Index slices are about 39 GB each and get normal pages; large pages are
  unavailable at that size once memory is fragmented. The 4.3 GB count array
  did get large pages.
- Each pass costs one full regeneration (about 1.8-2.2 min) no matter how many
  partitions it covers. The tiny last pass is mostly that fixed cost. Evening
  out the passes or freeing a little more RAM could drop one pass (not done).

## 11. Lessons and gotchas

- **Atomics:** random atomic read-modify-writes on large arrays are very slow
  (about 116 M/s on 16 threads). Give each thread exclusive ownership instead.
- **Locality comes from batch size:** what made the counting step fast was
  keys per cache line within a batch, not finer sorting. A full radix sort was
  slower than coarse grouping with bigger batches.
- **Priority:** a `nice`'d test barely runs while a 16-thread solver is busy.
  Run tests at normal priority with fewer threads.
- **Concurrent work skews timings:** a compile and test during 17-5's search
  cut its rate to 143 M/s. That run's search time is not representative.
- **Patch scripts:** writing them through a bash heredoc turned `"\n"` into a
  real newline in C++ string literals several times, so the build broke. Patch scripts
  are now written as files.
- **Large pages:** they worked for the 4.3 GB count array but not for the
  39 GB index slices on this uptime.
