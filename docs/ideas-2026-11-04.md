# Speed-up ideas, 2026-11-04

Eight brainstorming agents read the code and notes (nothing was built or run by them), each on one
area: GPU kernels, search algorithms, pruning and duplicates, filters and the index, puzzle
mathematics, systems and scaling, 16-3 at 18 moves, unconventional approaches. This merges their
~250 ideas into one list, duplicates combined. Gains are their estimates unless marked measured;
nothing here is checked yet except where said.

Where things stand (`changes-2026-11-04.md`): left are 15-3 and 19-2 (2x2 boards, at least 17
moves, ~10 days each on the RTX 5060 Ti as the solver is now) and 16-3 (normal board, at least 18,
~7-8 days estimated, layout not built). A 2x2 pass is ~1 260 s of generation plus the Bloom tests
and the CPU's survivor check.

## Tier 1: structural ideas (large gains)

### 1. A free move block at the meeting point (three agents found it independently)

A row move only rotates one row. So the **row class** of a state (each row turned to its smallest
rotation; on 2x2 boards the piece's row pair shifted so the piece sits at x = 0, its y kept) is
unchanged by any number of row moves, and two states share a row class exactly when a block of
row moves (one per lane, on distinct lanes) turns one into the other. Likewise column classes.

In a shortest solution, the moves of one direction between two moves of the other direction are
on distinct lanes (a repeated lane would merge into a shorter solution), so the path is a
sequence of alternating row blocks and column blocks. Take the block that contains move a + 1.
The state before it is at most a moves from the start, the state after it at most b moves from
the goal, and the two share a row class (or a column class). So **a + b = L - 1 covers every
path of length L**: the left side streams one level less, and each node probes the goal side by
its class instead of generating ~32 children.

- 2x2 boards at 17 moves: `<5,4,7>` + the block, about the cost of today's 16-move runs:
  **~10-15 h instead of ~10 days** (15-30x).
- 16-3 at 18: `<5,6,6>` + the block, about the cost of its 17-move run (the bound per level
  gets one move looser, so somewhat more).
- In-RAM and web solvers: one more depth at the same cost (web 10 -> 11 moves).
- Index: the goal side stores row classes of goal states whose first move away from the goal is
  a column move, and column classes for the rest (a state reached last by a row move has the same
  row class as its parent): about one goal set in all, so about today's pass count. The goal
  side must hold every depth up to b, not only depth b.
- A hit (left node, goal class) gives a candidate; confirm it, find the lane shifts and count
  them: length = a' + (lanes shifted) + b'. Periodic rows: compare shifts modulo the period.
  Expected false class matches: tiny (estimates 100 to 1e6 per run).
- Recovery: expand each hit into the depth-(L - b) middles through the block's moves, so
  `recoverSolutionsFromMiddles` is unchanged (left depth 10 on 2x2 boards is already checked).
- Limit: +1 is the ceiling for this trick. A key unchanged by both row and column blocks is
  constant (the group is all of S36), so two blocks cannot be absorbed.
- Checks: brute-force unit test of the class key (periodic lanes, the piece rows), then
  `--solutions` runs: 19-4 / 16-1 / 6-4 at 16 as `<5,3,7>` + block (~25 min instead of ~9 h),
  17-2 at 14, 16-2 at 15. Expect EXACT MATCH and IDENTICAL SET.
- Effort: M-L (GPU class key: a 2^18-entry table per lane, ~768 KB; incremental, since a row move
  leaves the row class unchanged; the two-key index builds in `no_table_d7.hpp` / `no_table_d6.hpp`;
  `mbgpu_match_children` with the new key; middles expansion).

### 2. Passes the left side can target

Today a pass is a range of hash partitions, so every pass regenerates every leaf and keeps only
its share. Split the goal side by a property that only some moves change, and a node with r moves
left can skip the moves that cannot bring it into the pass.

- **2x2 boards, by the piece's position** (25 values; x changes only by piece-row moves, y only by
  piece-column moves): a parent outside the pass tries only the one piece move that lands inside
  it. The last level is then generated about once over the whole run instead of once per pass:
  ~15-20% now (generation is ~25% of a pass). Positions near the goal's own hold ~35-40% of
  goal states, so those get hash sub-passes. With idea 1, the row-class table splits by piece y
  and the column-class table by piece x.
- **General form**: partition by the colours of a few fixed cells, or by a hash of one colour's
  mask, both computable from the parent and the move before building the child.
- **What it enables**: cheap extra passes, so a deeper goal side (depth 8, ~1.5e12 states,
  ~150-170 passes): 17-move 2x2 runs at ~1 day without idea 1, and with idea 1, 18 moves on 2x2
  boards at about a 16-move run's cost. Effort L.
- Exact (pure reachability). Effort M for the piece-position form.

### 3. 16-3 specifically

- **Search it backwards** (stream from the goal, bound toward the start). 16-3's goal is
  anti-diagonal stripes (cell (r, c) = `seq[r + c]`), so near the goal the rotation bound stays
  low and the forward tree is 6-8x bushier than 18-3's or 14-3's at the same level (run logs).
  The start looks random, so the bound toward it should prune like other boards: possibly ~6x.
  The existing `--reverse` turns the bound off and refuses `--gpu`; a swapped board pair
  (`16-3~rev`, like `4-4@r2c3`) plus inverting the solutions avoids that. Check on a swapped
  16-2 at 15. Effort S.
- **Drop "tight" nodes before expanding them**: a node with no slack (h = limit + r) needs a move
  that lowers h, or it is dead. The logs show at most 3.4% of 16-3's busiest level have any
  surviving child. Test it per node from the bound's count words, generate only the moves that
  lower h, and do the same at the leaves: ~3-4x on 16-3, less elsewhere. Exact. Effort M.
- **Stream depth 7 on the GPU** (`MBGPU_MAX_DEPTH` 6 -> 7), needed for `<5,7,6>` unless idea 1
  makes `<5,6,6>` + block enough. Effort S-M.
- **Seed shards in random order**: under 1% overhead on the GPU, restart points, and an early
  answer on whether 18 has solutions at all.
- Estimate: 7-8 days -> ~2 days with tight-node lookahead -> under a day if reverse behaves like
  18-3 (both guesses).

### 4. Goal symmetries (cheap, exact)

- **15-3's goal**: mirror left-right (c -> 5 - c) with the colour swap (1 2)(4 5)(3 6) fixes it
  (the piece at x = 2 maps to itself; checked by hand by one agent, to confirm with the symmetry
  counter). Store and probe min(key(x), key(mirror x)): half the goal side, ~3 passes instead of
  6, ~1.5-1.8x. Combines with idea 1 (the mirror keeps rows as rows).
- **16-3's goal** is fixed by transposition: half the goal side; with idea 1 the column-class
  table is the row-class table transposed.
- 19-2's goal has none.

### 5. Dissection over colour masks (long term: 18-19 moves)

The cell mask of one colour (plus the piece position) is acted on by moves on its own, so it can
be the "guess" in a Schroeppel-Shamir / dissection search (Dinur-Dunkelman-Keller-Shamir 2012;
Fiat-Moses-Shamir-Shimshoni-Tardos 1989 for permutation groups): per guessed middle mask, list
exactly the left and right middles with that mask through a depth-4 frontier indexed by mask and
all 4-move tails, then join on the full state. Possibly 50-200x fewer nodes than today, ~1000x
combined with idea 1, with memory one slice at a time (natural work units). Repeated colours mean
many ties per lookup; heavy slices need further splitting. Prototype in Python on a small board
first. Effort L, confidence low-medium.

## Tier 2: the GPU pass (engineering)

Survivor path (three agents):
- **Asynchronous pinned output**: today the GPU stops while survivors are copied back with
  synchronous pageable `cudaMemcpy` (`flushOutput`) and repacked on the same thread
  (`ProbeQueue::sink`, a new 1.5 MB allocation per 64 k). Double buffers, `cudaHostAlloc`,
  `cudaMemcpyAsync` on a copy stream, a piece pool or in-place reads. Estimated 10-30% of a pass.
- **Leaner records**: the seed field is copied but never read; send key + seed (12 B instead of 28)
  and re-stream only confirmed seeds, or key + locator. 2.3x less PCIe and host traffic.
- **One atomic per warp** for survivors (stage them in shared memory).
- **Sort each survivor batch by key on the GPU** (CUB, ~1-5 ms): the CPU's bucket and fingerprint
  reads become nearly sequential, 1.3-3x faster CPU check; exact duplicates can be dropped by full
  state.

Bloom test (~half of a pass):
- **Batch the tests per warp**: today each thread tests its children one at a time, ~6 sectors in
  flight per warp, ~17% of the card's bandwidth. Stage in-range leaves in the (unused in leaf
  builds) `Stage` buffer and issue all loads before testing: 1.5-3x on the Bloom part.
- Two 128-bit loads per block instead of 8 scalar; evict-first cache hints.
- **Sort or bin leaves by Bloom block** before testing (TLB reach: the per-partition cost rises
  from ~1.4 to ~1.8 s past ~5.6 GB of blocks); or make blocks small enough for L2 once passes are
  cheap (idea 2). 15-30%, possibly 2-5x on the lookup part.
- Bloom blocks in 2 MB pages (`cuMemCreate` / `cuMemMap`).
- **Bloom block from the key's own unused bits** instead of a second `mixKey`; then a key-sorted
  batch is also in block order and index order.

Filters and pass planning:
- **Bloom bits, both directions**: fewer bits is measured slower (section 11). One agent's fit of
  the same data said more bits with more passes would be faster: **measured, 14 bits is ~28%
  faster per run** (see the end of this file and `changes-2026-11-04.md` section 14).
- **Even pass sizes** (19-4 ran 47 x 5 + 21; 6 x ~43 is the same total with smaller filters) and
  **fill the VRAM** at the chosen pass count with more bits (~11.2 bits at 6 passes: ~30% fewer
  survivors for free).
- **Choose bits and pass count at run start** from a short timed sample, cached per device.
- **Better static filters** (the goal keys are known in advance): a one-sector Elias-Fano block
  filter (sorted remainders per 32-byte block, 2.3-6x lower false-pass rate at the same size and
  still one sector per test), prefix / vector quotient filters (~0.5% at 10 bits), ribbon filters
  (~0.1-0.2% at 10 bits, 2-5 sectors per test), binary fuse filters (3-4 sectors).
- Free ~0.3-0.6 GB of VRAM for the filter (unused level buffer at 5-move streams, seed arrays,
  a smaller output buffer).

Leaf generation (~25% of a pass):
- **Incremental StateHash**: it is XOR-linear, so a child's hash is the parent's XOR two lane
  terms (StateHash itself unchanged); build the child board only for survivors. 1.5-2x.
- **Linear partition test**: make the partition a fixed GF(2) map of the hash, so out-of-pass
  leaves (~82%) are rejected in ~10 instructions without `mixKey`. 2-4x with the above. Every
  key producer (CPU, CUDA, Vulkan) must change together.
- 32-bit lanes in `expandFat`, skip masked amounts before building children, occupancy variants
  timed at run start (`__launch_bounds__` 2/3/4 blocks per SM).

CPU survivor check:
- Large pages for the host index with `--gpu` (off today), whole-bucket prefetch and AVX2 compare,
  smaller buckets (2^23-2^24 per partition: ~21-11 states, one cache line), fingerprints with the
  bucket.
- Wider fingerprints from the unused key bits 16-33: at 17 moves without units, ~1.1e10 candidates
  (~260 GB) at today's rate; a u8 extra cuts that 256x.

Launches: ~507 k launches and ~6.7 k reruns per pass; read counters through mapped pinned memory,
adaptive chunk margins, CUDA graphs. ~1-3%.

## Tier 3: small exact fixes

- **Periodic lanes on 2x2 boards**: `perm_stream_fat.tpp` uses `continue` for every lane, so a
  normal row like `ABCABC` emits shifts 4 and 5 that equal 1 and 2 (the normal-board stream uses
  `break` at the period). Fix in the CPU stream, `first_moves.hpp` and the GPU kernels together.
  ~0.5-2%. To check first: whether the 2x2 stream really emits these.
- **Drop goal states closer than the goal depth**: the depth-7 set (depth 5 + 2 moves) still holds
  states at distance 5-6, which cannot be meeting points of a shortest solution; ~3% smaller index.
- **Exact-depth masks for the left side**: drop stream nodes that are closer to the start than
  their depth (one probe of depth-6 nodes against the depth-5 set), or per-seed first-move masks:
  ~1.1-1.2x on every board.
- More commuting rules on 2x2 boards (normal column -> piece row, piece column -> normal row):
  ~0.5-2% per level. Measure the duplicate breakdown first.
- Junction bound: at a probing node whose last move is a column move, the remaining column moves
  are all on the goal side, so drop it if the worst row's rotation distance exceeds b.

## Tier 4: systems and scaling

- **Rent GPUs** (rough mid-2026 price guesses, to check): RTX 4090 ~2-2.5x a 5060 Ti at ~$0.35/h,
  RTX 5090 ~4x at ~$0.7/h, 96 GB RTX PRO 6000 (one pass) or H100 (HBM). The remaining ~20
  5060-Ti-days for ~$60-150, ~1-2 days on ~10 cards. Unnecessary if idea 1 works.
- Needed for rentals or many machines: a Linux CUDA build for sm_80/86/89/90/100/120
  (`src/gpu/build.sh`), kernel variants timed per device, a Docker image that qualifies each host
  (`test_gpu_stream` PASS plus a short `--solutions` run) before giving it work, a dispatcher
  (`mbq farm`: leases, heartbeats, retries, copying `.mid` files back), several CUDA GPUs per
  process sharing one host index, work units as arbitrary (partition range x seed shard)
  rectangles.
- **Integrity on untrusted or non-ECC cards**: a build stamp in every middles file (commit, exe
  and DLL hashes, GPU, driver; `--recover-from` refuses mixed builds); deterministic per-unit
  counters (leaves, in-range, Bloom-passed, candidates: units of one seed shard must agree on
  leaves, and their in-range counts must sum to it); a key checksum per seed shard; a Bloom-block
  checksum at the end of each pass (a flipped bit could miss a solution).
- Checkpoints inside a unit (64 slices, as 6-move streams already do) for spot instances and holds.
- **Telemetry per pass** (clocks, power, temperature, throttle reasons, PCIe link): 19-2's passes 3-5
  ran ~25% slower than pass 1 with no hold, unexplained.
- Possible GPU settings (the user's call): CUDA's P2 memory state, a lower power limit (the pass is
  latency-bound, ~2-4% slower for less heat), a VRAM cap of ~14.5 GB instead of 12.5 (15-3: 6 goal
  groups -> 5).
- Several units of one goal group in one process (build the index once).
- Free compute: Kaggle (2 x T4, 30 h/week), Colab L4, a university cluster.

## Ruled out (and why)

- **Reachability invariants**: the commutator of a row and a column shift is a 3-cycle, so the
  group contains A36, and a 6-cycle is odd, so it is all of S36: every colouring with the right
  counts is reachable. Parity filters are dead ends.
- **More symmetries**: only D4 x translations keep rows and columns as lanes (only D4 on 2x2
  boards); short relations beyond commutation are 6+ moves long (removing under ~1e-6 of the
  stream).
- **Lower bounds on 2x2 boards** by tables, splits or relaxations (removing the piece's glue halves
  the bound again): capped near log33 of the table size (section 13).
- **SAT/SMT, CP-SAT, cube-and-conquer, BDD symbolic search, PDDL planners**: far slower than the
  GPU search on permutation puzzles, or blow up; a BDD of the depth-5 set is a cheap curiosity.
- **Quantum (Grover)**: ~1e8 coherent iterations, thousands of logical qubits; not this decade.
- **Learned move ordering**: every state must be visited for a proof; only safe for choosing
  layouts or load balancing.
- **Disk merge-join at a balanced split**: ~48 TB; external-memory BFS to depth 8: ~24 TB.
- **Parallel collision search**: finds some meetings, proves nothing.
- **The game's scramble data**: start boards are the goal scrambled with large move counts; no
  designer structure to exploit.
