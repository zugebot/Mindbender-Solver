## 2. Recovery at left depth 11 (2x2) and 12 (normal boards)

18-move runs with `--block` put the middles 11 (2x2, `<5,5,7>` + 1) or 12 (normal, `<5,6,6>` + 1)
moves from the start. `recoverSolutionsFromMiddles` keeps the shared start half at 5 moves and
streams the rest per middle: 6 moves on 2x2 boards (unfiltered; 48^7 would be too many, so 7 is
refused there) and 7 on normal boards (filtered toward the start root by the rotation bound).
`solver_frontier.hpp` (left depth up to 12), `ssd/recovery.hpp` (case 12).

Checks (`testExactSolverRegression --recovery 12|11 <file>`, known solutions split at that depth
must come back exactly): 18-3_c17_896 at 12 + 5 in 2.5 min, 14-3_c17_1790 at 12 + 5 in 77 min,
19-2_c17_3960 at 11 + 6: all PASS. Measured in production (15-3 at 18): **~1 h per middle per
thread** on 2x2 boards (25 middles on 25 threads: 64-82 min on EPYC / i9 machines). This PC at
6 threads would have needed 10-11 h for 15-3's 75 middles.

## 3. The fleet: `mbq fleet` (`python/scheduler/fleet.py`, `fleet_worker/*.sh`)

One search's work units on rented Linux GPU machines; this PC stays in charge. It connects out over
SSH (key `~/.ssh/mindbender_fleet`, added to the rental account once), copies a source package
(`src/`, `include/`, `mouse/`, CMake files), and each machine builds the solver and the CUDA module
itself (`setup.sh`: `-march=native`, `src/gpu/build.sh` with `-arch=native`) and must pass
`test_gpu_stream` before it takes units. Units run detached (`run_unit.sh`, setsid nohup, one per
machine), so they survive this PC sleeping or the server restarting. Every 60 s `status.sh` reports
progress and exit codes; finished middles files are checked (puzzle, split, shard, block) and filed
in `state/shards/`, and the search's merge job (recovery, validation, promotion) runs here.
Failed, vanished or stuck units (no progress for an hour) are re-queued (at most 4 attempts);
`--checks C` (default 2) re-runs units on another machine and requires byte-identical files.

Added during the run (11-06):
- `mbq fleet run ... --front` (queue ahead of other searches), `--only m4[,m5]` (machines allowed to
  take it), `--no-promote` (merge without promoting; used for the placement searches, promoted by
  hand after checking). Fleet searches force `engine: ssd`, so 11- and 12-move searches work too
  (the in-RAM engine cannot merge shards).
- Every unit's full log comes home on completion, ok or failed:
  `docs/run_logs/fleet/<puzzle>_m<moves>_n<units>/<unit>.<machine>.ok|exit<code>.log`; each
  machine's setup and self-test logs go to `docs/run_logs/fleet/machines/` when setup ends.
- `fleet remove NAME` (without `--now`) drains: the machine leaves after its current unit.
  `fleet add` with the same name puts it back (setup re-runs, ~5-10 min).

## 4. Linux containers: what had to change

- `src/gpu/mbgpu.cu`: `uint64_t` is `unsigned long` on Linux but the kernels use `u64 = unsigned long
  long`; the C interface now casts (`asU` / `asC`, with a `static_assert` on the size).
- `src/utils/platform.hpp`: `memory()` caps total and available RAM by the cgroup limit (v2
  `memory.max` / `memory.current` minus `inactive_file`, or v1 `limit_in_bytes`); new `cpuCount()`
  caps `hardware_concurrency` by the CPU quota (v2 `cpu.max`, v1 `cfs_quota_us` / `cfs_period_us`).
  A container shows the whole host (256 GB, 256 threads), and the solver's RAM budget and thread
  count followed it; verified as 183 GB / 16 threads, 367 GB / 31, 123 GB / 31 on rented machines.
  `ssd/cli.hpp` uses `cpuCount()` for the default `--threads`.
- `fleet_worker/setup.sh`: the self-test passes `--device ""` (its default device name was "5060"),
  tees `selftest.log`, and caps `ram_gb` by the cgroup limit; the package includes `include/`
  (ghc `fs_std.hpp`).
- This PC: `build/findSolutions.exe` and `build/testKnownSolutions.exe` rebuilt (11-06). The old ones
  (10-12) did not know placement names (`15-3@r4c3`), so placement merges "failed validation"
  although every solution replayed.

## 8. The GPU output pipe (built, exact, off by default)

Idea: the stream's output copy (device to host) and the CPU sink ran synchronously after each
launch, so the GPU waited. `mbgpu.cu` now has a second output buffer set, pinned host memory, a
copy stream and a helper thread (`OutputPipe`): launch k+1 runs while k's output is copied and
sunk. Exact: 16-2 at 15 and 17-2 at 14 EXACT MATCH + IDENTICAL SET with it on, and 15-3's 1/500
slice gives the same 26,599,938 candidates. But on a 5090 it saved only ~8% (354 s vs 384 s per
pass, on a machine that was noisy that hour) and GPU use stayed ~40%: the CPU side, not the copy,
is the limit. It is opt-in: `MBGPU_OUTPUT_PIPE=1` (the info line then says "output pipe on").
Logs: `docs/run_logs/fleet/tests/m1/`.
