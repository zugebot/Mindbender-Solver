# Changes 2026-11-01: the GPU solver

The RTX 5060 Ti now does most of the work of `experimentDiskDepth6 --gpu 5060` on normal boards
(forward searches): the left stream with its Bloom test, the bound audit, the goal side's depth-6
index and the confirmation of candidates. Recovery got a reachability filter that is not
GPU-specific. Every change is exact: `test_gpu_stream` matches the CPU seed by seed, and every
end-to-end run below gives EXACT MATCH and IDENTICAL SET against `build/levels_final`.

Commits, in order:

| `7174b89` | the bound audit and the depth-6 index build on the GPU |

## 2. Setup

- **Two GPUs.** The RTX 5060 Ti (PCIe bus 1, x8, CUDA device 0, sm_120, 36 SMs, 16 GB) runs the
  solver; the GTX 1660 SUPER (bus 4, x4, CUDA device 1) drives the desktop (2560x1440 at
  119 Hz) and is never used by the solver. The 1660 showed Device Manager error 31: it was bound
  to driver 595.97 while the 5060 Ti used 610.88. The user installed 610.88 for it through
  Device Manager ("Have Disk", the `nvmd.inf` already in the DriverStore); no reboot was needed.
  Windows already gives every graphics preference to the 1660, so nothing had to be pinned.
- **Toolchain.** CUDA 13.0 (`nvcc -arch=sm_120`) with Visual Studio 2022 Community's MSVC
  14.44. The solver is built with MinGW, which nvcc cannot use, so the GPU code is a DLL
  (`build_gpu/mbgpu.dll`, `src/gpu/build.cmd`) with a plain C interface (`src/gpu/mbgpu.h`),
  loaded at run time by `src/solver/ssd/gpu_stream.hpp` (next to the exe, else
  `<exe dir>/../build_gpu`, or `--gpu-dll PATH`).
- **CPU heat.** A 16-thread CPU run (18-3, in RAM) took the i7 to 100 C and was stopped. GPU runs
  use `--threads 8` for their CPU parts.
- **Solver autostart off** (2026-10-30). The logon script (`mindbender_startup.cmd`) no longer
  starts `mbq daemon` / `mbq resume`; the watchdog, the Discord bots and the demo app still
  start. The queue is paused (`jobs.json`). Solver runs happen only when the user asks.

## 3. The first version (`426d7f4`, `7174b89`)

### 3.1 Stream

The GPU re-implements the CPU's left stream without its headers: `B1B2` layout, move codes
`dir * 30 + lane * 5 + (amount - 1)`, the canonical rules of
`perm_stream_detail::stream_lanes_dfs` (same-direction lanes ascending, a lane stops at its
period, commuting column-then-row pairs skipped, each seed's last move from
`ssd::buildLastMoves` as the previous move) and the rotation lane bound at every level
("both" mode, `bounds::LanePruneLeaves`).

- Level by level: one level buffer per depth (8 M nodes each, 1.3 GB in all); a level is
  processed in chunks whose children fit the next buffer, and each chunk's subtree is finished
  before the next chunk, so every launch is short (Windows' WDDM resets a GPU whose kernel runs
  about 2 s).
- Leaves: key = `mixKey(StateHash(leaf))`, tested against the pass's Bloom blocks in VRAM (the
  same split-block filter as `FingerprintRange`); the ~1% that pass are handed back and the CPU
  finishes them with `FingerprintRange::probeGroup`, so the candidates are the CPU's.
- Safety: only the device whose name contains `--gpu NAME` is opened; at most `--gpu-vram-gb`
  (default 12.5) of its memory; any CUDA error or unrecoverable overflow stops the run.
- First kernel: one thread per (node, lane), h from its definition for every child.

### 3.2 Checks

- `exportGpuVectors` (CMake target, `src/programs/tests/`): CPU reference data from the
  solver's own PermStream code, single-threaded. Nine cases from 1-1, 10-3, 9-3, 18-3 and 16-2
  (seed depths 2-4, stream depths 2-5, unpruned and pruned, with and without last moves); per
  seed the leaf count and the wrapping sum and xor of the leaf keys. A "CHLD" block holds 10-3's
  goal frontier at depth 4 with its child counts per partition and sorted unique child keys of
  partitions [40, 72). `--bench P S D L` exports every seed of one split for timing.
- `test_gpu_stream` (`src/gpu/`): every case must match seed by seed; the audit must pass on
  every pruned case; goal-side counts and keys must equal the CPU's; an empty Bloom filter must
  pass nothing and a full one every leaf. `--bench` times a stream, `--seeds N` takes the first
  N seeds, `--filter-gb G` installs a random Bloom filter at a real one's density.
- End to end: `--gpu 5060 --solutions build/levels_final/<file>`.

### 3.3 Bound audit on the GPU

`gpuAuditBound` replaces `bounds::auditLaneBound` with --gpu. It checks the GPU's own bound:
h equals `lane_bound::referenceBound` on the seeds and on the one- and two-move children of 64
seeds (~160 k states); on every edge of the full (unpruned) streams of 256 seeds (2048 below
stream depth 5) h changes by at most 1; and per seed the pruned stream keeps exactly the full
stream's leaves with h <= limit. 16-2: 21.9 G edges in 5.9 s, where the CPU audit streamed 2
seeds in 156 s. A failure turns the bound off, as on the CPU.

### 3.4 Depth-6 index on the GPU

`no_table_d6.hpp` with --gpu: the GPU counts the depth-6 children per partition
(`mbgpu_child_counts`), measures the de-dupe ratio on partition 0 (`mbgpu_child_keys`), and per
group of partitions generates, sorts (CUB radix sort), de-duplicates and writes the
fingerprints, bucket offsets and Bloom blocks straight into the index arrays in the CPU's
layout (`mbgpu_build_index`). 16-2: 100 s -> 11.2 s (2.31 G states). The first try returned
sorted keys and let the CPU write the index; that writing took 24 of 31 s on 10-3.

## 4. The node kernel (`eb05f22`, `3eff96d`): stream 122 s -> 12.6 s

Nsight Compute on the first kernel: compute-bound (SM 90%, memory 3%), but only ~10 of 32
threads of a warp active, and every child's bound cost 6 rotations x 6 lanes. Nsight Systems:
18% of the wall time between launches (169 k launches, each followed by a blocking read of the
counters).

| Step (16-2, first 200 k seeds, 3 GB random Bloom filter) | Time |
|---|---|
| first kernel | 7.81 s |
| one thread per node, incremental bound, measured chunk sizes | 0.95 s |
| register cap for 3 blocks per SM (80 registers) | 0.84 s |
| children staged per warp in shared memory | 0.78 s |
| moving lane's cells precomputed, branch-free far test | 0.75 s |
| separate builds for inner levels and leaves | 0.74 s |

- **Incremental bound.** A lane's count word holds, per rotation k (one nibble each), how many
  of its cells differ from the target lane rotated by k; its distance is the smallest nibble.
  A row move changes one cell of every column, so each column's word is the parent's minus the
  old cell's mismatches plus the new cell's: one lookup per column in a 288-entry table
  (`c_mc` / `c_mr`, built by `mbgpu_set_target`, copied to shared memory). The moved row's own
  distance does not change. The far test is SWAR: add (7 - room) to every nibble; a lane is too
  far iff all six bit 3s are set. The audit keeps the first kernel, so it also checks this.
- **Chunk sizes.** Sized from the measured children per node (80% of the next buffer) instead
  of the worst case of 60; a chunk that overflows its buffer is run again (inner levels: re-run;
  Bloom output: counters restored, the earlier leaves handed over, then halves). 16-2: 5 k
  launches instead of 169 k.
- **Staging.** Children go through a per-warp shared buffer (160 entries) and are written in
  contiguous runs with one atomic per flush; written from registers, a 32-byte sector carried
  ~7 useful bytes.
- Tried and dropped: skipping a lane when a crossed lane is too far even without the moving
  cell (0.79 -> 0.82 s: divergence), 2 or 4 blocks per SM (shared memory allows only 3; the
  4-block register cap spills), a tighter register cap for the leaf build.
- Where it stands: about 0.63 ns per parent node at every level; inner levels 64% of the
  kernel time, leaves 36%. The 30 bound tests per lane are the floor of this design.

## 5. Around the stream (`4b1a65f`, `7531182`)

- **Candidate check on the GPU** (`mbgpu_match_children`): regenerate depth 6 and keep the
  children whose key is a candidate's (binary search); the CPU compares the full states.
  16-2: 15.8 s -> 1.2 s.
- **CPU probe overlapped.** The Bloom survivors go through a bounded queue (`ProbeQueue`,
  64 M leaves) to `threads` probe threads while the GPU streams. Before, they were collected and
  probed after the stream: 16-4 at 14 held 620 M leaves (~15 GB) and probed for 20 s with the
  GPU idle. Stream + probe 71 s -> 53 s; the probe now ends 0.01-0.06 s after the GPU.
- **No CPU memset** of the Bloom blocks (the GPU writes them all), and **large pages off** with
  --gpu: the CPU probes ~1% of the leaves, and allocating 18.8 GB of large pages on fragmented
  RAM took 9.6 s on 16-4. Index 35.6 s -> 27.9 s.

## 6. Recovery (`3b0d683`): 58 s -> 6.3 s on 16-2

Recovery built every path of depth (left + 1) / 2 from the start to meet each middle's own half
(16-2: 760 M paths, 44 s on one thread, ~24 GB). It now keeps a path ending d moves from the
start only if some middle is within left - d moves by the rotation lane bound (one
`LaneTables` per middle, `RecoveryReach` in `solver_frontier.hpp`). The bound is 0 at its
target and changes by at most 1 per move, so it never exceeds the distance: no path to a middle
is lost. 16-2: 760 M -> 3266 paths, 44.3 s -> 5.4 s; the per-middle half is then streamed
against the small shared half instead of stored and sorted (9.3 s -> 0.9 s). Normal boards, at
most 64 middles (`recoveryReachMaxMiddles`; each node is checked against every middle). The
in-RAM solver uses the same code; `testExactSolverRegression` passes (14 checks). Recovery logs
the time of both parts.

## 7. How to run

```bat
src\gpu\build.cmd
cmake --build cmake-build-test --target experimentDiskDepth6
build_test\experimentDiskDepth6.exe 16-2 --seed-depth 4 --stream-depth 5 --threads 8 --gpu 5060 ^
    --solutions build\levels_final\16-2_c15_366.txt
```

`build_test/` holds the solver build with --gpu (`cmake-build-test`, `MB_OUTPUT_DIR=build_test`);
`build/experimentDiskDepth6.exe` and the scheduler do not use the GPU yet. A 16-move normal
board: `--seed-depth 5 --stream-depth 5 --gpu 5060` (about 4 min on 18-3).
