## 2. The stream kernel (122 s -> 12.6 s on 16-2)

Nsight Compute on the first kernel (one thread per (node, lane), h from its definition for every
child): compute-bound (SM 90%, memory 3%), but only ~10 of 32 threads of a warp active, and
every child's bound cost 6 rotations x 6 lanes. Nsight Systems: 18% of the wall time between
launches (169 k launches, each followed by a blocking counter read).

| Step (16-2, 200 k seeds, 3 GB random Bloom filter) | Time |
|---|---|
| first kernel | 7.81 s |
| one thread per node, incremental bound, measured chunk sizes | 0.95 s |
| register cap for 3 blocks per SM | 0.84 s |
| children staged per warp in shared memory | 0.78 s |
| moving lane's cells precomputed, branch-free far test | 0.75 s |
| separate builds for inner levels and leaves | 0.74 s |

Tried and dropped: skipping a lane when a crossed lane is too far without the moving cell
(0.79 -> 0.82 s, divergence), 2 or 4 blocks per SM, a tighter register cap for the leaf build.

The incremental bound: a lane's count word holds, per rotation k (one nibble each), how many of
its cells differ from the target lane rotated by k; the distance is the smallest nibble. A row
move changes one cell of every column, so each column's word is the parent's minus the old cell's
mismatches plus the new cell's (one lookup in a 288-entry table per column). The far test is
SWAR: add (7 - room) to every nibble, then a lane is too far iff all six bit-3s are set.

## 3. Around the stream

- **Candidate check** on the GPU (`mbgpu_match_children`): regenerate depth 6, keep children
  whose key is a candidate's. 16-2: 15.8 s -> 1.2 s.
- **CPU probe overlapped**: the Bloom survivors go through a bounded queue to the probe threads
  while the GPU streams. 16-4 at 14: stream + probe 71 s -> 53 s (the probe had waited for the
  whole stream, holding 620 M leaves, ~15 GB).
- **No CPU memset** of the Bloom blocks (the GPU writes them all) and **no large pages** with
  --gpu: allocating 18.8 GB of large pages on fragmented RAM took 9.6 s on 16-4.

## 4. Recovery (58 s -> 6.3 s on 16-2)

Recovery built every path of depth (left + 1) / 2 from the start (16-2: 760 M paths, 44 s on one
thread, ~24 GB) to meet each middle's own half. It now keeps a path ending d moves from the start
only if some middle is within left - d moves by the rotation lane bound (one table per middle).
The bound is 0 at its target and changes by at most 1 per move, so it never exceeds the
distance: no path to a middle is lost. 16-2: 760 M -> 3266 paths, 44 s -> 5.4 s; the per-middle
half is then streamed against the small shared half (9.3 s -> 0.9 s). Normal boards, at most 64
middles (each node is checked against every middle). Also used by the in-RAM solver;
`testExactSolverRegression` passes (14).

## 5. What is left

- 17 moves on normal boards (14-3, 18-3) as `<5,6,6>`: the GPU streams depth 6 already; the
  solver side (stream depth 6) and recovery (left depth 11, a shared half of 6) need it.
  Estimated 1-2 h per puzzle from the depth-5 rate (not measured).
- 2x2 boards on the GPU (fat moves, the depth-7 index in slices).
- The scheduler does not pass --gpu; `build/experimentDiskDepth6.exe` predates it (the GPU runs
  above used `build_test/`).
- The kernel: ~0.63 ns per parent node at every level; the 30 bound tests per lane are the
  floor of this design. More needs a stronger bound (pattern databases on the GPU, whose memory
  is idle) or fewer nodes.
