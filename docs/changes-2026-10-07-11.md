## 4. The colour-mix lower bound (d71737d, 753bed5)

### 4.1 The idea

A row move rotates one row: that row keeps its colour multiset (the same
colours, shifted), and every column has exactly one cell changed. A column move
is the mirror image.

So look at the colour multisets:
- For row `r`, let `R_r` = how many of its cells' colours are not in the
  target row's multiset (6 minus the common count). Row moves never change `R_r`.
  Each column move changes at most one cell of row `r`, so it lowers `R_r` by at
  most 1. So at least `R = max_r R_r` column moves are still needed.
- Likewise `C = max_c C_c` row moves are still needed.
- Row moves and column moves are different moves, so **h = R + C** moves are
  needed in total. It never overestimates (it is admissible).
- **One move changes h by at most 1.** A row move leaves every `R_r` alone and
  changes each `C_c` by at most 1, so `C` changes by at most 1 and `R` not at
  all; the same holds for a column move. This is the "step 3" that makes parent
  pruning legal: if a node has `k` moves still to come below it and
  `h > limit + k`, none of its descendants can get within `limit` of the
  target, so the whole subtree is skipped.
- On 2x2 boards one move can shift two lanes, so `h = ceil(R/2) + ceil(C/2)`.
  At these depths it never exceeds the table depth, so it prunes nothing, and
  the solver turns it off on 2x2 boards.

Check: `experimentBoundSample --check` evaluates it on all 1.89 M states of
every known optimal solution path (each state's true remaining distance is
known): 0 violations.

### 4.2 Making it fast

The goal was the same order of cost as a move (the bit-packed board shifts run
at ~1.5 G states/s across 16 threads).

| Version | ns/state, one thread |
|---|---|
| Reference (count colours per lane, min per colour) | 33 |
| SWAR (4-bit counters in a u32 per lane) | 17 |
| **Lane tables** (shipped) | **8.5 (7.5 net of the loop)** |

Lane tables, built per puzzle at run start (22-30 KB, fits L1):
- Each 6-cell lane (18 bits of colour) maps through a first table (u16) and a
  second table (u8) to a small "colour mix id". The ids are capped: all mixes
  at or beyond the largest useful mismatch share one id.
- For each lane position, a table maps the id to a one-hot distance mask.
  OR-ing the six rows' masks and taking the highest bit gives `R` without
  branches; the same for columns.
- Matches the reference on 60 M states.

### 4.3 Where it is used (`--bound` modes)

| Mode | What it does |
|---|---|
| off | nothing |
| leaf | don't look up left states with `h > table depth` |
| both | leaf, plus drop any stream node with `h > depth + moves still below it` |
| parent | the parent prune only, no per-leaf check |
| pdb / pdbleaf / pdbparent | the same with the pattern-database tables added (section 5) |

The parent prune runs through a new PermStream hook (`PARENT_PRUNE` template
parameter, `skipMask<BELOW>`). It is asked per lane at every level above the
leaves. The default `NoParentPrune` compiles to nothing: same checksum and
speed with it off.

### 4.4 Audit and calibration (every run, `--bound auto`)

1. **Audit** on this run's own seeds: the fast bound equals the reference,
   `|dh| <= 1` on every sampled edge, and a pruned stream keeps exactly the same
   wanted leaves as the full stream. Any failure: the bound is off.
2. **Calibrate**: rotate the real seeds through every available mode for
   20 s per 3 modes (26.7 s with 4 modes, 46.7 s with 7) and keep the fastest,
   if it beats off by at least 3%.

## 5. Pattern databases (2420916, a17da53)

### 5.1 Single colours: too weak

For one colour, the abstract board has its cells as 1 and the rest as 0. It is
solved exactly by BFS over every placement, using the real move code. It is
admissible (0 violations over 460 k lookups on the known paths), but a single
colour is too easy: max distance 8-9, so the bound rarely exceeds 6-7. Lookups
skippable at 14 moves: 17-5 23.5% (colour-mix) -> 47.4% (either), 16-4 41.7%
-> 43.6%; 2x2 boards 0-4%. Not integrated.

### 5.2 Grouped classes: integrated

Merge several colours into one class (e.g. colours 0, 1, 2), so the abstract
puzzle is harder (max distance 10) while staying exactly solvable:
- Index: colex rank of the class's cell positions (of the blank cells when the
  class has more than 18), x 25 piece positions on 2x2 boards. A 10-cell class
  has C(36,10) = 254 M entries.
- 2 bits per entry: `code = min(3, max(0, distance - limit))`, so one table
  serves pruning up to 2 levels above the leaves. 254 M entries = 64 MB packed,
  built in ~30 s at 16 threads.
- Up to 3 classes per puzzle, the largest that fit 300 M entries each, chosen
  per puzzle; a run builds them in 10-90 s.
- The hook asks once per lane with all 5 shifted nodes, so the pruner computes
  and prefetches every table entry before testing any (the one-at-a-time
  version waited on each cache miss).
- Audited per run like the bound (0 at the target, every child of a far node
  far on sampled real edges, identical wanted leaves).

Measured: 16-4 at 13 moves, `pdbparent` skips 37% of last levels: search
1016-1034 s -> 682 s (1.5x). Leaf-level checks were slower than off there: a
39% skip does not pay for a check on every leaf, which is why the parent-only
modes exist.

In the 14-move queue the tables were chosen for 16-2 (`pdb`), 17-1 and 17-3
(`pdbparent`), and the re-run of 16-4 (`pdbparent`).

### 5.3 Open issue: calibration under-rates `pdbparent`

- 16-4 at 13 moves: calibration said 1.10x, the real run was 1.5x.
- 16-4 at 14 moves (first try, job #116): `off` 4073 us/seed vs `pdbparent`
  4059 us/seed, so it ran with no bound, even though the audit showed the
  tables raising the last-level skip from 8.4% to 39.1%.
- The re-run (#139) timed `off` at 7887 us/seed (the machine was busier) and
  picked `pdbparent` at 1.10x.

The likely cause is that the modes are timed in interleaved slices that
disturb each other: `pdbleaf` alone costs 13.5-15.1 ms/seed and evicts the
tables from cache. Fix ideas: time each mode in its own longer block, drop
modes that lose badly after the first slice, or let `--bound` be set per job
from the scheduler.

## 7. Work units (58609be)

One search split into independent pieces, for several runs or PCs:
- **Solver:**
  - `--shard k/N` keeps only the seeds with index = k (mod N).
  - `--middles-out FILE` writes the middles found (usually none) to a small
    text file. It has a puzzle/split/shard header and an `end` line, and is
    written atomically.
  - `--recover-from FILE...` merges shard files and recovers and validates as
    usual. It refuses a missing, duplicate, truncated or mismatched shard.
- **Scheduler:**
  - `mbq add P --moves M --shards N [--remote k,...]` queues local shard jobs
    plus a merge job. The merge job waits for every result without blocking
    the queue.
  - `mbq export` builds a folder for another PC: the portable solver, a
    one-click `.bat` per shard, and a README.
  - `mbq import` files the returned `.mid`.
- **Portable build:** `-DMB_MARCH=x86-64-v3 -DMB_OUTPUT_DIR=<repo>/build_portable`
  (AVX2/BMI2, no AVX-512), in `build_portable/`.
- **Bug found in testing:** the exported `.bat` failed with "exe not
  recognized" (Windows' NoDefaultCurrentDirectoryInExePath). It now runs

## 8. Scheduler and machine setup

- **Re-queue after a reboot (7d1096a):** when the server starts and the
  running job's solver is gone, the job is marked interrupted and the same job
  is queued again at the front (it keeps its split and `--until`).
- **Hold solver (e3be8f0):** `Pause` only stops the next job from starting.
  "Hold solver" suspends the running solver's threads (NtSuspendProcess, the
  same as Resource Monitor's "Suspend Process"). Its RAM, progress and files
  stay as they are, and "Release solver" continues from the same point.
  - The flag is saved, so it survives a server restart (not a reboot).
  - A second hold is a no-op, and Cancel works while held.
  - The ETA takes held time out of the phase's clock.
  - Each hold is noted in the job's history.
  - CLI: `mbq hold`, `mbq unhold`. The dashboard has a yellow banner while
    held, and the header button is now "Pause queue".
  - Tested on a dummy process, then for 15 s on 15-3 (progress froze, then
    continued). The user then used it for 38 min on 15-3.
  - A held solver keeps its RAM (~40 GB). Only a cancel frees it, and a cancel
    loses the run (as on 10-11 for the local-AI test).
- **Splits:** `table = 7 if (2x2 and moves >= 14) or moves >= 16 else 6;
  stream = 4 if moves - table >= 9 else 3`. `--stream-depth` overrides. Seeds
  make up the rest.
- **Startup (Windows Startup folder, `mindbender_startup.cmd`):**
  `mbq daemon` + `mbq resume` from the repo folder, then `call "E:\runner.bat"`
  (the three Discord bots), then a console running the demo app in the repo
  folder. Delete the file to stop it. Pausing Windows Update and auto-login
  are left to the user.

## 11. Lessons and gotchas

- **Prune at parents, not at leaves, when the skip rate is low.** A per-leaf
  check costs about as much as the lookup it saves unless it skips more than
  ~80-90% (16-4: 40% skip, leaf mode 1.4x slower than off; 17-3: 80%, even; 15-1: 96%,
  1.2x faster). Dropping a whole last level from its parent saves every leaf
  under it for one check.
- **Batch and prefetch table lookups.** Asking per lane for 5 nodes at once,
  then prefetching, made the pattern-database prune pay off.
- **Calibration by interleaving can mislead** when one mode thrashes the
  cache (section 5.3).
- **Benchmarks need a quiet machine:** pause the queue and stop the running
  job (a run with tests alongside, 14-4 and 18-3, ran slower).
- **Job waiters:** waiting for "the next job to finish" fired early on
  cancellations. Wait on a specific job id.
- **Windows macros:** `far` is a macro in the Windows headers; a variable
  named `far` broke the build.
- **Patch scripts** go through the Write and Edit tools, not bash heredocs
  (which turned `"\n"` into real newlines again).
