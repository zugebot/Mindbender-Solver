## 2. 16 moves on normal boards: `<5,5,6>`

The scheduler allowed at most 15 moves for the ssd engine, although the solver handles a left
depth of 9; lifting that (040ed54) queued 16-move runs as `<5,4,7>`. 18-3's run showed this
split cannot work on normal boards:

- depth-5 goal frontier 114 M states -> 2.9e11 raw / ~1.6e11 unique depth-7 states: an
  **819 GB** fingerprint index;
- RAM budget **11.1 GB** (the depth-7 bucket counts alone held 17.2 GB, see section 3; the
  OS and other programs ~10 GB) -> **86 passes**;
- every pass streams the whole left side: the bound calibration measured 1.8 ms per seed, 160 M
  seeds on 16 threads = ~5 h per pass, **~430 h** for the puzzle. Cancelled after 1.3 h.

The other way to split 16 moves keeps the goal side at depth 6, which fits in one pass (18-3:
4.4e9 states, 18.7 GB), and puts the extra move on the left: a 5-move stream from the depth-5
seeds. Unpruned that is ~8e8 states per seed, but the rotation bound prunes at every level, and
more tightly the shallower the goal side is (a node with r moves to go is dropped when
h > 6 + r instead of 7 + r). Measured on 18-3 with `experimentBoundSample --deep` (rotation
bound, per seed):

| Split | Nodes visited | Lookups | Passes |
|---|---|---|---|
| `<5,4,6>` (15 moves) | 3.5 k | 0.27 k | 1 |
| `<5,4,7>` (16) | 215 k | 149 k | 86 |
| `<5,5,6>` (16) | 435 k | 18 k | 1 |

So `<5,5,6>` costs about two `<5,4,7>` passes in total, ~40x less. 18-3 then ran in **8.5 h**
(one 18.7 GB pass, 4.9 ms per seed per thread with "both").

Code (30b802e):

- `ssd/probe.hpp`: `--stream-depth 5` (`streamAndProbeT<5>`; `PermStream` already went to 5).
  At stream depth 5 the bound calibration times only the modes that prune at every level
  ("both", "parent"): "off" and "leaf" generate the whole 5-move tree (16-2: ~47 s per seed per
  thread, ~25 min per 512-seed timing block). The first test run spent its time there; with the
  change the timing took 26 s.
- `ssd/recovery.hpp`: left depth 10 (`recoverMatchedMiddlesGlobally` already allowed it).
- `bounds/audit.hpp`: at stream depth 5 the audits sample 8 seeds (was 256) and compare pruned
  vs full streams on 2 (was 32), so they take minutes (16-2: 155 s).
- `python/scheduler/mbq.py`: 16 moves = `<5,5,6>` on normal boards, `<5,4,7>` on 2x2 boards
  (where the bound prunes nothing, so a deeper left side would not help); `--stream-depth 5`
  accepted by `add` and `export`.
- Exactness: 16-2 as `<4,5,6>` = 15 moves (the 5-move stream and its pruning, recovered through
  left depth 9): middles 15/15 **EXACT MATCH**, solutions 366/366 **IDENTICAL SET** (57 min).
  Recovery through left depth 10 compiles but has not recovered a solution yet (18-3 found no
  middles); the first 16-move solve will be its test (it replays every solution anyway).

The test solver was built in a separate tree (`cmake-build-test`, `-DMB_OUTPUT_DIR=build_test`)
so the scheduler kept copying the old exe until the change was checked.

## 3. Depth-7 goal side without a table (for 2x2 boards at 16 moves)

Not yet run end to end: no 2x2 16-move job has run since. Test on 18-4 (a 2x2 15-move puzzle,
partition subset holding its known middles) before queuing one. In `ssd/no_table_d7.hpp`:

- **Bucket counts spilled to disk.** The count pass keeps a u16 per index bucket for all 256
  partitions (2^25 buckets each for 18-3: 17.2 GB), and they came out of the index budget. They
  are now written to a temp file on the system drive (NVMe) and each pass reads its partitions'
  slice back (~2% of the pass's index; reserved from the budget). `--d7-counts-ram` keeps the
  old behaviour. For 18-3 this would have meant ~28 GB for the index instead of 11 GB.
- **Goal-side filter (normal boards).** A meeting point is within L = seed + stream depth of the
  start, so depth-7 goal states with rotation h(start) > L are dropped in the count, fill and
  verify streams alike (exact). `experimentBoundSample --goal-side 18-3` measured how much it
  saves: it keeps 54% of 18-3's depth-7 states (h(start->goal) is only 10, so most of the goal
  side is still "within reach" of the bound), and no depth-5 state can be skipped. It is on by
  default for normal boards (`--no-goal-filter` turns it off), but normal boards no longer use
  depth 7 at 16 moves.
- **Partition subsets without a table.** `--d7-partitions N [--d7-first-partition F]` used to
  force the disk path; the no-table path now honours them (counts, index and probe cover only
  those partitions), which makes cheap exactness tests possible.
- `BigArray::reset()` frees an array early (`fingerprint_index.hpp`).

Rough estimate for a 2x2 board at 16 moves (`<5,4,7>`, no bound; not measured): a 15-move-sized
index (~230 GB, ~7-8 passes with the budget freed above), each pass streaming ~25x the 15-move
left side: still ~200-300 h per puzzle on this CPU (CLAUDE.md roadmap 1, 2, 4).

## 4. experimentBoundSample --goal-side

`experimentBoundSample --goal-side <puzzle> [--table-depth T] [--left-depth L] [--samples N]`:
for sampled depth-5 goal states streamed T - 5 moves, the share with h(start) <= L (could still
be meeting points), rotation and colour mix, and the depth-5 states with h <= L + T - 5.

## 7. Findings (no code)

- **Why the depths level off at 14-16.** A puzzle's boards are the arrangements of its goal's
  colours: 10^4 to 10^27.4 of them. Moves multiply the reachable boards ~33x each (16-2: 6.9e7
  at depth 5), so 15 moves reach ~10^23. Grouped by board count, the optimal depths follow it
  closely (10^12-10^16 boards: 3-12 moves; 10^24-10^28: 15-16+). The game builds each puzzle by
  random moves from the goal (`data\mindbenders.txt` stores the count: 99 for 34 puzzles), so
  puzzles are typical boards, not worst cases.
- **Counting lower bounds.** Canonical move sequences (rows commute with rows, columns with
  columns) grow 40.8x per move; a colour mix with more boards than sequences of length d has a
  board needing more than d moves. Most 8-colour mix (4,4,4,4,5,5,5,5, 10^27.7 boards): some
  board needs >= 18 moves; 16-3's colours: >= 17; 36 distinct tiles: >= 26. Proving a 20-move
  board exists is out of reach.
- **Loopover.** Mind Bender is 6x6 Loopover with colours. Loopover's God's number is studied
  in single-tile moves (one unit shift = one move): 6x6 is between 36 and 86 (coolcomputery,
  2023). Our solutions measured that way: 18-1 is the longest at 31 unit shifts (40 counting
  both lanes of each 2x2 move); 1.59 unit shifts per move on average; within one puzzle the
  optimal solutions can differ 2x (11-1: 15-30).
- `build/levels_final` holds an extra, non-optimal file for 4-4, 9-4, 10-4, 11-4, 12-2, 12-4 and
  13-4 (solutions one move longer than the optimum). Left in place.

## 8. Loopover God's number port (separate repo: `X:\loopover-gn`)

A C++ port of coolcomputery's Java (`github.com/coolcomputery/Loopover-Brute-Force-and-
Improvement`, MIT; the original kept in `reference/`), for bounding 6x6 Loopover's God's
number. Not part of this repo; its README documents it. Three programs, each checked against
the Java:

- `phasebfs`: every position of one block-building phase, 2 bits per position in RAM (depth
  mod 3), push then pull, all threads. 24/24 identical depth distributions (8 phases x 3
  modes), including 6x6 `000001 -> solved` with God's number 24 as published. 4.7x their Java
  on one thread (40 M positions).
- `improve` (`BFS2improve`): alternative first-phase solutions for scrambles over a threshold,
  with their move pruning and symmetry reduction; 13/13 identical verdicts on 3x3-5x5 chains.
- `improve --mitm` (`BFS_DFS`): meet in the middle for what is left; 18/18 verdicts equal to the
  combined region's exact God's number.

Next there: the 6x6 phases `010101 -> 000101` (4.5e9 positions) and `000101 -> 000001`
(6.1e10, ~15 GB), which need the machine between solver jobs.
