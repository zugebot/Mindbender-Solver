# Changes 2026-10-29 to 2026-10-30: the first-move rule

Everything here follows from GitHub issue 1 by the user's teacher (`algorithm0r`), who found
that the canonical left stream applied its move-order rules to every move except the first one
from each seed, and sent a patch with a proof sketch and 10-3 measurements. This document is the
complete write-up; sections 13 and 14 of `changes-2026-10-16.md` are the short addenda written
as the work went along.

Commits: `b5431bc` (the rule on normal-board seeds), `9173a0f` (lanes stop at their period),
`ed871d8` (the rule on 2x2 seeds and on both goal sides; shallow states dropped).

## 1. The waste

A search `<S, T2, T>` streams every depth-S seed T2 more moves with `stream_lanes_dfs`
(normal boards) or `stream_fat_lanes_dfs` (2x2 boards). Inside a stream, consecutive moves obey
the canonical-order rules: same-direction lanes strictly ascending (so two row moves on different
rows appear in one order only, and a lane is never shifted twice in a row), no move that gives the
board back, and a normal column followed by a normal row only when the pair does not commute
(the row-then-column order keeps that board). The moves below the first one therefore average
about 41 choices on a normal board and about 33 on a 2x2 board. The first move from each seed
had every choice, 60 or 48, because the seeds came from the frontier builder as bare states and
the stream started with "no previous move".

Each extra first move carries a whole subtree, and all of it is wasted: a first move on the
seed's own last lane merges with that move (the board is at depth <= S, nothing below it can be
a middle), and a first move the rules would have put earlier repeats a subtree that another seed
streams in the allowed order. Before the bound, the stream was 60/41 = 1.47x (normal) or
48/33 = 1.45x (2x2) larger than it needed to be.

The same boundary existed on the goal side: the no-table depth-6 index regenerates every
depth-5 state's 60 children (16-20 times per build, in slices), and the depth-7 goal side streams
every depth-5 state 2 moves with an unrestricted first move. And the 2x2 left stream was not in
the issue's patch at all.

## 2. The rule

Every state of a layer gets the last move of its lexicographically smallest path from the root,
with moves ordered the way the streams visit them: rows before columns, lanes ascending, amounts
1 to 5 (a fat lane counts at its first index). The stream is started with that move as the
previous one, so its first move follows the rules too.

Why nothing is lost. Take a board B at distance exactly S + T2 from the root (the board at
position S + T2 of a shortest solution; the goal side's argument is the same with the goal as
root) and its lexicographically smallest shortest path P. Its first S moves reach a seed Q and are
the smallest path to Q, otherwise swapping in a smaller path to Q gives a smaller path to B. None
of P's adjacent pairs is one the rules skip: a same-lane pair merges into a shorter path to B,
impossible; an out-of-order pair of the same direction, or a commuting column-row pair, swaps
into a smaller path to B, impossible; a no-op shortens it. So the stream from Q, started with Q's
last move (which is P's move S), produces B. Each rule is a "swap or merge gives a smaller or
shorter path" rule, which is exactly what the argument needs; a rule that only dropped moves by
their amount would not qualify (section 6).

The layers are not BFS layers. The frontier builder's "exact depth d" layer is every endpoint of
a d-move sequence without no-op moves, deduplicated within the layer only, so it also holds
states shallower than d (1-1's layer 2 holds root + R3 shifted twice, a depth-1 state). The
argument is about states at distance exactly d, and the coding below gives every one of them its
smallest shortest path's last move, by induction along that path. A shallower state may have no
rule-following d-move path at all; see section 5 for what happens to those.

## 3. What was built

- `perm_stream_detail::forEachFirstMove(board, prevMove, fn)` (`src/chuzzles/first_moves.hpp`):
  the children a canonical stream visits first after `prevMove`, in visiting order, with their
  move codes (`dir * 30 + lane * 5 + amount - 1`; `NO_PREV_MOVE` = every first move). Normal and
  2x2 boards, with the streams' own rules: fat lanes move as a pair, one amount per fat lane is
  illegal (it would put the 2x2 piece across the edge), the commuting rule applies between normal
  lanes only, and on normal boards a lane stops at its period (section 4).
- `ssd::buildLastMoves(root, depth, layer, out, threads)` (`src/solver/ssd/common.hpp`): rebuilds
  layers 1 to depth and codes them forward. A state's code is the smallest (parent's code, move)
  over the rule-following moves of the coded layer above (6 bits per move in a u32, so depth
  <= 5). Each child is looked up in a hash table of its layer (`StateIndex`: slot = index + 1,
  linear probing, load <= 1/2) and lowers that state's code with an atomic min. Only the last move
  (one byte per state) is kept. The issue's version found each seed's move with 60 binary searches
  per seed into the layer above; coding the other way round, it is 60 lookups per state of the
  layer above instead: 18-3's 160 M depth-5 seeds in 29 s instead of 209 s.
- `streamDepth` / `streamDepthPruned` take an optional previous move; `stream_lanes_dfs` and
  `stream_fat_lanes_dfs` gate their order checks on "there is a previous move" instead of
  `CUR_DEPTH > 0` (every other caller passes nothing and is unchanged).
- The probe codes the seeds after shard selection; `no_table_d6` and `no_table_d7` code the goal
  side's depth-5 frontier (`g_goalMoves`) and expand it with `forEachFirstMove` / the 2-move stream
  started with each state's last move (count pass, index builds and verification all use it).
- `ssd::dropUncoded` removes the states that got no code (section 5).
- Flag: on by default for every run; `--no-seed-last-move` streams every first move, as before.
- Tests: `testExactSolverRegression` gained `testLastMovesCoverNextLayer` (5 puzzles, normal and
  2x2, depths 1 to 3: the coded moves equal a brute force over every parent and move, and
  streaming each state one move with its last move reaches every state at the next exact
  distance), and `testDfsStreamMatchesMaterializedPerms` now requires the DFS stream to be a
  sub-multiset of the materialized list with the same set of states (it compared multisets, which
  encoded the old repeats). 14 checks pass. `testLanePrune` (5.7 M masks, 1008 pruned streams,
  8.7e9 leaves) still passes.

## 4. Lanes stop at their period (normal boards)

Also from the issue: in `stream_lanes_dfs` the "shift gives the board back" check was a
`continue`. The first amount that gives the board back is the lane's period (1, 2 or 3), and every
larger amount repeats a smaller one, so it is now a `break`. It is safe because the two masks
evaluated below it, the commuting mask and the parent prune, are properties of the resulting
board, and a periodic lane stays periodic under its own shifts, so a repeat amount gets the same
decision as the amount it repeats. Not applied to the 2x2 stream: a fat lane drops one amount by
its number, not by the board, so a larger amount that repeats it must still run. The regression
test's 6-2 segment check fails with a `break` there, which is how that was found.

## 5. Shallow states are dropped

A state of the depth-S layer that is really shallower than S can never be the depth-S state of a
shortest solution, and a goal-side depth-5 state that is shallower has no child at exact depth 6
(or descendant at depth 7). Those states get no code when they have no rule-following S-move path
(a lane shifted twice, for instance), and a state at exact distance S always gets one, so the
uncoded states are removed from the seeds and from the goal frontier before the search
(`dropUncoded`). Some shallow states do have a rule-following path and stay; they are harmless.

This makes the solver stricter about finding only solutions of the searched length. The lower
bounds were always built that way (every length is run in turn, each run proving "no solution of
exactly this length"), so nothing changes for the scheduler. A one-off run at length N without
N-1 having been run would no longer find a shorter solution by accident, as it sometimes did.
