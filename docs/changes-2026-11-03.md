## 2. The Linux port

The solver, the Vulkan module and the GPU test now build and run on Linux. The Windows code
paths are unchanged, and the Windows builds in `build_test/` compile with the changes.

- **`src/utils/platform.hpp`:** the few operating-system calls, for both systems:
  - memory figures (`/proc/meminfo` on Linux)
  - 64-bit file seeks
  - the process id and the exe's own path
  - shared libraries (`LoadLibrary` or `dlopen`)
  - page-aligned zeroed memory
- **The solver:** `common.hpp`, `fingerprint_index.hpp`, `probe_sink.hpp`, `no_table_d7.hpp`,
  `disk_depth6.hpp` and `experimentDiskDepth6.cpp` call it instead of Win32.
- **Large pages on Linux:** the probe index uses `mmap` with `madvise(MADV_HUGEPAGE)`
  (transparent huge pages) where Windows asks for large pages.
- **GPU modules:** `gpu_stream.hpp` loads `libmbgpu.so` / `libmbvk.so` on Linux, and
  `mbgpu.dll` / `mbvk.dll` on Windows. `mbgpu.h` exports with `visibility("default")` on
  Linux.
- **Build:**
  - The solver builds with the existing `CMakeLists.txt` (Ninja, g++ 13.3, Release,
    `-DMB_MARCH=native -DMB_OUTPUT_DIR=<dir>`).
  - `src/gpu/vulkan/build.sh` (glslc + g++) builds `libmbvk.so`, `test_vk_stream` and
    `vk_devices`. It is the Linux twin of `build.cmd`.
- **Which GPU drives a monitor:**
  - Windows: DXGI adapters that have an output.
  - Linux: the PCI addresses of the connected DRM outputs (`/sys/class/drm/card*-*/status`).
- **`test_gpu_stream --no-audit`:** skips the slow full-stream audits, for quick checks while
  tuning.

**Correctness, first runs:**

- 10-3 at 13 on one GPU: EXACT MATCH, 1648 solutions.
- 16-2 at 15 on one GPU, then on three: EXACT MATCH, 366 solutions.
- 17-4 at 13 (2x2) on three GPUs: EXACT MATCH, 166 solutions.

**Tuning for GCN** (details and the table in `src/gpu/vulkan/README.md`, "Measured"):

| Normal boards | First port | Registers | Crossed lanes | RTX 5060 Ti (CUDA) |
|---|---|---|---|---|
| bench 16-2, 200 k seeds, one GPU | 8.04 s | 4.43 s | 3.27 s | 0.74 s |
| 16-2 at 15, stream + probe | 45.4 s (3 GPUs) | 21.2 s (4 GPUs) | 13.1 s (4 GPUs) | 12.6 s |

- **Registers (1.8x):** the first port kept a lane's 5 children in arrays, as the CUDA kernel
  does, and RADV gave the node kernel 128 VGPRs, so 2 waves per SIMD. Now:
  - a lane's children are a 5-bit mask, and each child is rebuilt from its parent when it is
    used;
  - staging is 4 bytes per child (parent slot, move), with the parents in LDS.

  That brought the kernel to 64 VGPRs (2x2: 40), and LDS from 28 KB to 12.8 KB.
- **Crossed lanes (1.36x):** a move changes one cell of every lane it crosses, so a crossed
  lane's distance changes by at most 1. Only crossed lanes already at the room left can go over
  it, and only those are looked up now (usually 1-2 of 6). Exact: every audit identical.
  **The CUDA kernel still tests all six**, so the same change should speed up the 5060 Ti on
  normal boards. Not done yet: it needs the GPU here idle for its A/B.
- **2x2 boards** did not change. They wait on random Bloom reads, about 1 G per second per GPU
  (GDDR5's random-access rate). Tried without gain: 16-byte loads, five reads in flight, fewer
  count words in registers, and skipping the test when a node has slack.
- **One buffer, 4 GB:** RADV caps a single allocation at 4 GB (`maxMemoryAllocationSize`). The
  first 18-3 run therefore planned its Bloom filter as 2 passes, which would have doubled its
  time. The filter now spans up to 8 buffers (`bloomBuf[8]`, `bloomPartsPerBuf` partitions
  each). 16-2's 366 solutions came out identical with the filter forced into small pieces;
  18-3 then ran in 1 pass. NVIDIA reports no cap, so CUDA is unaffected.

At full load the GPUs hold 1243 MHz at 80-97 W (cap 98 W), and four GPUs scale 4x. With the
changes above, the four of them are about even with the RTX 5060 Ti on both board kinds.

## 4. Several GPUs, chosen at run time

`--gpu [cuda:|vulkan:]NAME` picks the module and the devices at run time; nothing is
hardcoded per machine.
- **No prefix:** CUDA first, then Vulkan.
- **`auto`:**
  - CUDA takes its first device.
  - Vulkan takes every discrete GPU that drives no display. If there are none, it falls back
    to the display GPUs, then other GPUs, never a CPU implementation.
- **Explicit choices:** `all`, `#N`, or part of a name. Several are separated by commas.
- **`--gpu-list`:** prints every device and which ones `auto` takes. It opens none.

Every chosen Vulkan device works on the same run:
- **Shared work:** the stream, the checksums, the audit, the child counts and the candidate
  check hand out seeds in chunks from one shared counter, so a faster card simply takes more.
- **The Bloom filter:** each pass's blocks are copied to every device, so more GPUs make a pass
  faster, not fewer passes.
- **First device only:** the goal-side index build and `mbgpu_bounds` (they need one sorted
  set).

This machine still runs CUDA on the 5060 Ti (`--gpu 5060`), and its kernels are byte for byte
the same. The Vulkan module has not yet run on the 5060 Ti.

**A pitfall found on the friend's PC.** When the monitor is off or unplugged, no DRM output is
connected. `auto` then cannot tell which GPU drives the screen and takes all four. On
2026-11-03 at 18:50 that sent 14-3 onto the monitor's GPU, which reached 96 C. There the
monitor's GPU is Vulkan `#0` (PCI 0c:00.0; `vulkaninfo` lists pciBus 12 first), and the other
three are `#1`-`#3` (06, 07, 0d). Runs there now name them: `--gpu "vulkan:#1,#2,#3"`.

## 6. Goals the game also accepts

The game counts a board as solved when every cell shows the goal's colour. So where the goal
has another 2x2 block in the 2x2 piece's colour (not across an edge), the piece may end there
too, and the game accepts it. An audit of the 28 puzzles with a 2x2 piece found **7 puzzles
with 22 such placements**:
- 4-4 and 9-1: 4 each.
- 13-5: 8.
- 17-2 and 19-2: 1 each.
- 15-3 and 19-4: 2 each.

**How placements are stored and named:**
- Each placement is its own puzzle, `<p>@r<row>c<col>` (the piece's top-left cell,
  1-indexed): `4-4@r3c4` is rows 3-4, columns 4-5.
- Placements are never counted as official answers.
- Their solutions are in `build/levels_final/game_accepts/`, and their bounds in their own
  section of `build/README.md`.

**The code:**
- `levels.hpp`:
  - `BoardLookup::gameAcceptedFats`: the other blocks of the goal piece's colour.
  - `gameAcceptedName`: makes the `@` names.
  - `getBoardPair("4-4@r3c4")`: builds a placement's board pair and caches it.
  - `name` is 16 characters now.
- `testKnownSolutions`: reads `@` names.
- `mbq`: accepts `@` names. A solve goes to `game_accepts/` and changes only that
  placement's README line; the official list and `config.json` stay as they are.
- Chuzzle Suite: see section 7.

Searched with `findSolutions` from 3 moves up, one depth per run, each answer checked by
`testKnownSolutions` and the scheduler's replay:

## 7. Chuzzle Suite (was the demo app)

- **Queue tab** (now the second tab: Solutions | Queue | Speed Chuzzle | Saves | Launcher):
  - It reads the scheduler's HTTP API (`queue_client.py`) and shows the running job, its
    phases, a progress bar and the time left.
  - It also shows the queued jobs, a stats strip, and the solver log with the live line.
  - Hold and Pause buttons; Pause needs a second click.
  - It only reads unless a button is clicked, and the app works without the scheduler.
- **The window:**
  - It draws its own title bar (`title_bar.py`, `window_frame.py`) with a pin that keeps the
    window on top; the pin is remembered in `user_data/settings.json`.
  - A 440x150 mini view of the running job.
- **Game-accepted goals:**
  - Puzzles that have placements get a yellow dot in the grid.
  - *< Goal* / *Goal >* in the preview steps through the official goal and each placement,
    with its solutions.
  - Placements are labelled "not the official goal" in yellow.
- **Renamed** on 2026-11-03:
  - `python/demo_app/` -> `python/chuzzle_suite/`, the package `chuzzle_demo` ->
    `chuzzle_suite`, `run_demo.py` -> `run_suite.py`.
  - The window title is Chuzzle Suite, and the header says Chuzzle Solver.
  - The environment variable is `CHUZZLE_SUITE_MBQ_URL`.
  - The logon script starts `run_suite.py`, and `mbq`'s replay imports from the new folder.
- **As a Windows program:**
  - `assets/make_icon.py` draws the icon: the title bar's four chuzzles on a dark tile, written
    as `.ico` (16-256 px) and `.png`.
  - `install_shortcut.py` makes a Start menu shortcut (pythonw, no console; output goes to
    `user_data/chuzzle_suite.log`). It carries the AppUserModelID `Mindbender.ChuzzleSuite`,
    and the app sets the same id on itself.
  - The window also carries the relaunch command, name and icon, so pinning the running window
    pins the app, not plain pythonw. A pin made before that fix shows Python's icon and must
    be unpinned and pinned again.
  - Windows 10 lets no program pin itself; pinning is one right-click.
