## 2. 2x2 boards on the GPU

**Stream (`expandFat`).** One thread per node, as `expandNodes`, with the rules of
`perm_stream_detail::stream_fat_lanes_dfs` and `forEachFirstMove`:
- the piece's two rows (columns) move together; the second lane of the pair is skipped;
- the amount that would move the piece across the board's edge is skipped
  (`1 << (4 - fatX)` for rows, `1 << (4 - fatY)` for columns);
- a lane does not stop at its period (moving the pair changes the piece's position bits);
- the commuting column-row skip applies only to a normal row after a normal column move;
- no bound (on 2x2 boards the halved lane bound prunes nothing; the solver already turns it off,
  and `mbgpu_set_target` refuses a limit on them).

The child output (staging per warp, leaf counts, checksums, keys, Bloom test) moved into
`emitLane`, shared by both kernels; the normal-board cases still match, and the stream speed on
normal boards is unchanged.

**Goal side.** The goal-side calls (`mbgpu_child_counts`, `_child_keys`, `_build_index`,
`_match_children`) take a depth: 1 regenerates the depth-6 goal side from its depth-5 frontier,
2 the depth-7 one.
- Depth 6 (`no_table_d6.hpp`): the GPU index and candidate check now run on 2x2 boards too.
- Depth 7 (`no_table_d7.hpp`, 2x2 boards with `--gpu`): the count pass is per partition on the
  GPU (3.5-3.9 s instead of ~374 s, and no 4 GB of u16 bucket counts or their temp file); each
  pass's index is built on the GPU in the depth-6 layout (contiguous sorted unique keys per
  partition, so no bucket counts are needed), in groups of partitions whose raw keys fit the
  device (~24-30 regenerations of depth 7 per pass, ~60 s per 8.5 G unique states); candidates
  are confirmed by regenerating depth 7 on the GPU (45 s for 10 M candidates on 18-4).
- The ratio of unique to raw keys (which sizes the Bloom blocks) comes from partition 0's exact
  sorted keys instead of a 1/4096 sample.

**Passes.** With `--gpu`, pass planning also keeps a pass's Bloom blocks within the GPU's free
VRAM minus 256 MB (`mbgpu_vram_left`). At 10 bits per state and the 12.5 GB cap that is ~10.9 GB,
~8.7 G goal states per pass, which on 2x2 depth-7 goal sides (37-45 G states) gives 5-6 passes,
about the same as the RAM budget (~60 GB) allows.

**Where 18-4's 25 min went:** 6 passes x (index ~60 s + stream ~205 s), 45 s candidate check.
The stream ran 1.59 T leaves per pass at ~7.9 G/s on the full passes, and 2.5x faster on the
last, a third the size (3.5 GB of Bloom blocks instead of 10.6 GB): the Bloom lookups are what
cost, and they get slower as the filter grows.

**16 moves on 2x2 boards (`<5,4,7>`)**, projected from 18-4: one more streamed move multiplies
the leaves by ~31 (17-2's measured fan-out), so ~6500 s per full pass, ~10 h for 5-6 passes per
puzzle (CPU estimate: 200-300 h). Fewer passes would need a smaller filter per state (VRAM) and a
smaller index (RAM); see the CLAUDE.md roadmap.

## 3. Recovery: per-middle start side

Recovery joins a shared start-side frontier (depth 5 at 16 moves) with each middle's own paths
back toward the start (depth 5), streamed. The 2026-11-01 reach filter (`RecoveryReach`) shrinks
the shared side to the paths that can still reach a middle, but only up to 64 middles (it tests
each path against every middle). 12-1 had 119, so every middle streamed ~0.8 G paths and looked
each up in a 776 M-entry array: 61 s per middle per worker, 2 h in all.

Now the per-middle stream keeps a state j moves from the middle only if the rotation lane bound
to the start root is at most TOTAL_LEFT_DEPTH - j (the start root is within that many moves on
any solution through it). Exact for the same reason as the reach filter: the bound is 0 at its
target and changes by at most 1 per move. One target per middle, so it costs nothing extra with
many middles. 12-1: 7262 s -> 6.3 s for the middles (the unfiltered shared side, 46 s, is now
most of the 56 s). 16-2: 6.3 s -> 5.7 s. Normal boards only (the bound is useless on 2x2).
